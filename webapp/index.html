            S2S Threat Sandbox
            
Server-to-Server Security Threats & FAPI Defenses

            

              Server-to-server tokens typically carry high financial privileges (such as treasury sweeps, bulk payroll, or direct debit authority).
              If an attacker leaks or exfiltrates an M2M token, standard OAuth 2.0 Bearer tokens leave the entire bank account vulnerable.
              See how FAPI 2.0 prevents disaster:
            

          

        


        

          
          

            

              🖨️
              

                
Threat 1: Token Leaked in Server Logs / APM

                
An engineer accidentally prints the access token to Datadog or ELK. Hacker extracts it and replays with Authorization: Bearer.

              

            

            

              
            

          


          
          

            

              👾
              

                
Threat 2: Rogue Service with Own Key

                
A compromised microservice in the cloud gets the stolen token and crafts its own DPoP proof using its own EC key.

              

            

            

              
            

          


          
          

            

              ⏳
              

                
Threat 3: Stale / Pre-computed Proof

                
Attacker attempts to replay a captured proof or use a pre-computed signature against a nonce-protected endpoint.

            Technical Reference
            
Why FAPI for Server-to-Server (M2M)?

          

        


        

          
1. Why Not Just Use Traditional Client Credentials?

          

            In RFC 6749, the Client Credentials grant traditionally relies on a client_id and a static client_secret.
            Once authenticated, the Authorization Server returns a standard Bearer access token.
          

          

            In high-value corporate banking (Corporate Treasury, Automated Clearing House, SWIFT messaging, Regulatory Reporting), this creates severe systemic risks:
          

          
    
            
  • Shared Secret Vulnerability: Both the client and the AS must store the secret. If either side or transit is compromised, the secret leaks.
    • 
            
  • Bearer Token Exfiltration: S2S tokens often have 10-60 minute lifetimes and broad privileges. If an attacker dumps server memory, intercepts traffic via SSRF, or reads application logs, they can drain accounts from any machine in the world.
    • 
            
  • No Cryptographic Non-Repudiation: Shared secrets cannot prove which party created an assertion.
    •
